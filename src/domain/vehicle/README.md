# Vehicle domain (0.I-1)

Pure TypeScript and immutable edit/preview operations. No filesystem or save-write API is used by the domain. Game source and personal saves were read-only inputs during development.

## Public API

Import from [index.ts](./index.ts). Definitions use the shared structural contract `Definition { id: string; type: string; [key: string]: unknown }`. Pass `{ parts: Map<string, Definition>, items: Map<string, Definition>, flagRequirements?: Map<string,string> }`. The maps must contain the **active mod-order-resolved** definitions; this domain does not flatten inheritance or combine namespaces. Build `flagRequirements` from active `json_flag` definitions' `requires_flag` fields. Omitting that map causes explicit incomplete-dependency warnings.

- `createVehicle(name)`, `renameVehicle(vehicle,name)`, `partsAt(vehicle,x,y)`, `setPartVariant(vehicle,index,variant)`.
- `installPart(vehicle,{id,x,y,variant?},indexes)` and `removePart(vehicle,index,indexes)` return `{ vehicle, ok, issues }`; failed edits return an unchanged clone.
- `validateVehicle(vehicle,indexes)` checks installation order, structure/adjacency, duplicates, location/cargo conflicts, mirror/opaque conflicts, engine exclusion groups and supplied flag dependencies. It is **not full game validation**. Removal checks basic attachment/dependency/structural-split rules; dynamic animal, carried-vehicle and lock-state game interactions are not comprehensively simulated.
- `calculateStats(vehicle,indexes)` returns metric records `{ known, missing, complete, unit }`, not fictional zeroes for missing contributions. Weights use grams, capacities millilitres, power watts / hp. `known` is a known subtotal when `complete === false`. `missing` counts uncomputed contributions, not necessarily distinct parts. Actual power is explicitly unavailable, not the rated-engine sum. No speed, acceleration, consumption or range estimate is provided.
- `createProject(vehicle,metadata)`, `updateProject(project,vehicle,event?)`, `parseProject(input)`, `serializeProject(project)`. The project retains independent `original` and edited `vehicle` snapshots, metadata, ordered mods, history, warnings and unknown fields. Shared save lossless JSON preserves large integer and exponent tokens throughout clone/edit/project round-trips. Ordinary unsafe JS numbers are rejected rather than silently rounded. Projects are **editor-only** and cannot be injected into game saves.
- `getFuelChoices(vehicle,indexes)` reports per-part allowed options, proven capacities and unsupported reasons.
- `previewMigration(vehicle,{ includeCargo, condition:'preserve'|'new', fuelSelections?:Record<number,string> },indexes)` returns `{ vehicle, changes, issues, fullyRenewed }`. `changes` is a per-part field-level preview. Only `part.items` is cargo; installed tools and base contents are not stripped. The original vehicle is never changed. `new` clears serialized base `damaged`, `degradation`, and `faults`, not cargo item damage.
- `exportBlueprint(vehicle,{id?,modId?,dependencies?},indexes)` returns `{ prototype,modInfo,losses,files,gameValidated:false }`. `exportBlueprintZip` returns a `Uint8Array`. Official prototype fields only, stable prefixed auto-IDs, sanitized filenames and explicit loss report. Supply the real ordered dependencies: the domain does not guess mod ownership. Structurally invalid blueprints fail; unknown IDs remain exportable with warnings.
- `importVehicleFile(string|Uint8Array)` reads a project JSON, prototype JSON or this editor's blueprint ZIP. It returns `{vehicle,project?,issues}`. Prototype imports preserve the raw original under `importedPrototype` and per-part `blueprintSpawn`; they do not pretend probabilistic spawn instructions are actual save items. Re-export preserves supported fuel/ammo/tools and item spawn descriptions. Unsupported original fields remain in the project but may be absent from native blueprint output. ZIP import is bounded (16 MiB compressed / 32 MiB expanded / 8 MiB entry / 32 entries) and rejects unsafe paths and ambiguous vehicle entries.

## Read-only part specifications (0.2.0)

`describePart(partId, indexes, baseItemIdOverride?)` returns `PartDetails` with typed sections/fields, `known | default | unknown` status, source roles, unit/reference/note codes, installed-part versus base-item qualities, pseudo-tool qualities, permitted connectable tools, and complete composed public definitions for advanced inspection. Optional `indexes.toolQualities` supplies quality definition metadata. This API never mutates the definitions, vehicle project or save state.

- `epower` is watts: positive generation versus negative fixed electrical draw. `energy_consumption` is full-load engine energy input, includes losses and varies with demand; only battery-fueled engines are labeled electrical draw. `power` is mechanical output, while negative alternator power is mechanical load. Horsepower uses 745.6998715822702 W/hp. These are ratings, not net available vehicle power.
- Cargo `size`, item external `volume`, container pockets, battery charge limits and ammunition alternatives are separate. Pocket restrictions and unsupported finalization are not flattened into a fictitious total. A static nominal tank volume does **not** add support for liquid refill/migration.
- `qualities` are tool capabilities, not character skills or installation requirements. Installed part qualities, base-item qualities and pseudo-tool qualities remain separate. `JACK` / `LIFT` use 500 kg per level; `SELF_JACK` is a distinct self-jacking check and has no inferred general-purpose lifting capacity. Charged pseudo-tool qualities remain conditional.
- The UI shows static ratings for both palette and installed selections independently. Instance damage/degradation, enabled state and recorded nested charges/tools are shown separately; absent state is not filled with zero/false, and no fuel/electric total or live performance is fabricated. All descriptions are plain text with CDDA color tags removed.
- Uninterpreted public fields are accessible in advanced data; that is not a claim of complete simulation. Source defaults are annotated and uncertainty is gated per affected field rather than suppressing unrelated known facts.

## Read-only vehicle systems overview

`analyzeVehicleSystems(vehicle, indexes, purpose = 'self-propelled')` analyzes the edited snapshot against the **current active composition**. `purpose` is `self-propelled` or `passive`; this is a report preference, not vehicle/project metadata. The function does not install, remove, enable, refill or repair anything. Its report is separate from `validateVehicle` installation/removal rules and never blocks project or blueprint export.

- Engines, energy stores and electrical equipment are listed per installed part, with mount coordinates and definition IDs for traceability. Reliable definition flags and fields determine roles; names, ID substrings and category labels are not substitutes for source semantics. Missing definitions remain unknown rather than becoming zero-power/non-engine parts.
- Mechanical engine output, full-load engine input, electrical demand, generation and mechanical load remain distinct static ratings. Negative engine `epower` is running ignition/ECU demand, **not starter-only** ([vehicle.cpp:5433–5463](../../../../0.I-branch/src/vehicle.cpp#L5433-L5463)); startup uses a separate formula and is not simulated ([vehicle_use.cpp:706–724](../../../../0.I-branch/src/vehicle_use.cpp#L706-L724)). Battery-only engine full-load input contributes once to nominal electrical demand; mechanical output is not added to it. Mixed battery/other-fuel options do not establish the selected mode: optional battery-mode input is shown separately and the main demand remains incomplete. No net-power, current-output, fuel-use, range or driveability calculation is implied. For example, the real `engine_electric_small` has 7.04 kW mechanical output and 8 kW full-load electrical input, not 15.04 kW consumption.
- Reliable installed `base.typeid` takes priority over the part's default item for nominal storage; the optional `describePart` base-item override is used only to resolve that identity, not to invent instance contents. Missing actual item definitions cannot borrow a different default item's capacity. Alternative ammunition capacities, multiple or restricted pockets are not blindly added; unsupported totals remain unknown.
- Battery capacity, nominal liquid-container volume and recorded instance contents are separate evidence. Battery energy conversion is 1 charge = 1 kJ, so kWh = charges / 3600 ([vehicle.cpp:1196–1201](../../../../0.I-branch/src/vehicle.cpp#L1196-L1201)). The real `storage_battery` magazine restriction is 50,000 battery charges; the real `tank` base item provides a 60 L watertight container pocket, not its 60.05 L external item volume. Nominal capacity does not prove a fuel is present, a battery is charged, a liquid is compatible, or that migration/refill is supported. Missing instance fields are not filled with zero or an invented full state.
- Completeness checks are static component evidence, not game certification. Self-propelled purpose asks about propulsion and driving components; passive purpose makes missing propulsion/driving components not applicable rather than blocking an intentionally unpowered structure. Existing structural validation remains independent. Unknown or incomplete relevant definitions cannot establish a clean bill of health.
- Driving `CONTROLS` and electrical `CTRL_ELECTRONIC` are different source flags: an electronic control panel is not proof of steering/accelerator/brake controls. Likewise a `BOARDABLE` part alone is not proof of an appropriate seat, and a nominal fuel store is not proof of a compatible fueled engine. Flags must be interpreted for the specific check, without guessing from labels.
- Fuel-route compatibility respects reliable exact storage-part `fuel_type` restrictions in addition to nominal capacity/ammo category ([vehicle_part.cpp:409–445](../../../../0.I-branch/src/vehicle_part.cpp#L409-L445)); gas/plasma containment remains unknown when a potential tank exists, not a false definite missing. Unmodeled pocket constraints such as minimum item length and ablative/holster behavior remain unsupported. Omitted but explicitly unresolved power/epower fields remain unknown electrical contributions rather than silently disappearing from known-zero totals.
- A starter-battery check is added only when potential faults explicitly establish `fault_engine_starter`; combustion fuel or negative `epower` alone is not that evidence. Unresolved fault groups stay unknown instead of implying no starter ([vehicle_use.cpp:706–724](../../../../0.I-branch/src/vehicle_use.cpp#L706-L724), [item_factory.cpp:4168–4180](../../../../0.I-branch/src/item_factory.cpp#L4168-L4180)). Pure boats and wheelless rotor designs are not universally required to have road wheels; flotation, flight and special steering remain unverified.
- `summarizeVehicleSystems(report)` is the pure aggregation API shared by the overview and disclosure summaries. It returns `totals`, `loadComponents`, `fuelCapacities` and `groups.{engines,stores,electrical}`. Each group carries original per-instance `members` plus its own totals. The stable grouping key is system kind + part ID + resolved actual/default base item ID, never the translated name. Different state/damage/content records stay in the same model group; every instance is summed independently. All `Metric` values preserve known subtotal, unknown count and completeness; invalid/overflowing inputs cannot become trusted zeroes. `fullLoadInput` is the source definition's fuel/electrical `energy_consumption` rating, not a model of human metabolism or environmental energy input; an external-energy engine's default zero is not a claim of zero total real-world energy use. `summarizeSystemCapacities` is shared by legacy report capacity fields and new totals/groups so unknown counts and overflow handling cannot diverge.
- The all-on nominal electrical demand includes source-backed accessory drain, engine-running auxiliaries, battery-only engine full-load input, and active `RECHARGE` demand, once per physical part. `RECHARGE` `bonus` is already **W**, not legacy numeric kW: a real recharge station adds 600 W; the workbench recharger adds 15 W charging + 50 W overhead ([map.cpp:5496–5571](../../../../0.I-branch/src/map.cpp#L5496-L5571)). Optional battery-mode engine input is separate, not an assumed selected fuel. Unsupported epower roles stay unknown rather than becoming fictitious continuous draw.
- Recognized alternator/solar/reactor/engine/water ratings are nominal generation, not a simultaneous guarantee. A wind turbine's epower is a wind-dependent coefficient, so its fixed contribution remains unknown ([vehicle.cpp:5466–5521](../../../../0.I-branch/src/vehicle.cpp#L5466-L5521)). `POWER_TRANSFER` epower encodes percentage cable loss and contributes no generation/demand rating ([vehicle.cpp:5784–5799](../../../../0.I-branch/src/vehicle.cpp#L5784-L5799)). Neither startup surge nor dynamic tool/turret use, connected-network deficits or cargo deficits are included in fixed installed ratings.
- Tank reserve is the **sum of nominal tank volumes**, not the largest single tank or an exact fuel-specific quantity; mass limits and compatibility still apply. Rated battery energy and separately recorded battery charge are never substituted for one another. Other fuel/ammunition capacities are summed only within unambiguous compatible ammo types, not across alternative resources. Known installed disabled/damaged parts remain in design ratings and carry per-instance warnings.
- Repeated models render as native, initially collapsed disclosures with count, group totals and instance-state notices. Singletons display directly. Outer category summaries retain installed counts, model counts and principal totals when closed. Language, disclosure and report-purpose changes are read-only and never alter project/history/export.
- The UI report appears after the existing vehicle statistics as **动力、能源与完整性 / Power, energy & completeness**. **校验用途 / Validation purpose** changes only this read-only report; changing purpose or language must not add an edit/undo event or alter project snapshots. No report state is serialized into project export.

Check status is `present | missing | conditional | unknown | not-applicable`; missing-component checks are advisory, not errors. Fuel-supply matches establish only a nominal storage route; charged/fueled state, external power, starter requirements, remote/animal control conditions, flotation under real mass and all runtime behavior remain conditional or unknown where appropriate. Wheel evidence permits a single `STABLE` wheel only for at most three structural tiles; it does not evaluate actual loaded roadworthiness. Relevant source: [vehicle_use.cpp:1990–1994](../../../../0.I-branch/src/vehicle_use.cpp#L1990-L1994), [game.cpp:5927–5996](../../../../0.I-branch/src/game.cpp#L5927-L5996), [vehicle.cpp:4984–4997](../../../../0.I-branch/src/vehicle.cpp#L4984-L4997).

Real definition evidence: [motor.json:3–16](../../../../0.I-branch/data/json/vehicleparts/motor.json#L3-L16), [motor.json:43–51](../../../../0.I-branch/data/json/vehicleparts/motor.json#L43-L51), [battery.json:151–155](../../../../0.I-branch/data/json/items/vehicle/battery.json#L151-L155), [containers.json:2893–2915](../../../../0.I-branch/data/json/items/containers/containers.json#L2893-L2915). ## Explicit partial support

- **No game executable/import verification has been run.** Static TS tests are not game validation. Every export includes that warning.
- Refill supports only one directly installed `MAGAZINE` pocket with an exact `ammo_restriction` and a compatible recognized serialized pocket. Free fuel/ammunition choice is always explicit per part; an old/default ammunition type is never auto-selected. Fixed battery refill requires unambiguous battery ammunition data. Multi-pocket items, liquid tank volume/charge conversion, detachable magazines, nested fuel capacity and installed-tool refills are currently **unsupported**: retain their original contents/quantities, issue warnings and return `fullyRenewed:false`. The UI must not label these 'all full'.
- Composed definitions use `_incompleteFields:string[]` for field-level reliability (nested dotted paths are supported). Only relevant fields invalidate a calculation: e.g. inherited `to_hit`/`melee_damage` uncertainty does not invalidate an explicit frame weight, while `weight`, `flags`, charge-counting fields or `pocket_data` uncertainty affects the metrics/rules that actually depend on them. `_incomplete:true` without a valid field list, or a list containing `'*'`, remains conservatively unknown globally. Affected metrics carry missing counts/warnings; installation/removal rules do not assert untrusted flags/location/engine semantics, part-to-item associations are fabricated only when `item` is reliable, and refill never trusts unresolved capacity fields.
- Static weight supports ordinary base items, charge-counted ammo/non-solid comestibles/stackable items, known nested pockets and installed tools without double counting. `stack_size` is not a weight divisor. Corpse/craft state, runtime mass overrides, gun-modified base weights, ammo-belt linkages and extra-pocket weights are incomplete. Complex cargo volume, charge-counted cargo volume and container expansion rules are not guessed. Unknown IDs contribute missing counts.
- Durability follows serialized `base.damaged` (not an invented `part.hp`). 0.I-1 non-charge-counted item max damage is 4000, charge-counted max damage 0. Rated power excludes condition-dependent muscle/animal/wind contributions. Current engine power needs fueled/enabled state, damaged-power factor, faults, alternator load and multi-engine reduction and is deliberately unavailable.
- Blueprint output is lossy: exact damage/degradation/faults, fuel quantities, containers/complex cargo, ownership, passengers, world references and arbitrary mod state are not transferable as native vehicle prototypes. Top-level item IDs are retained as spawn descriptions; instance details are reported as lost. Full raw preservation requires the project format.
